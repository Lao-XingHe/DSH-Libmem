# B4 检索性能修复记录

> 日期：2026-09-21
> 范围：`services/B4_dual_gate_retrieval/`（附带 `config.yaml`、`services/C2_mcp_server/mcp_server.py`）
> 结论：`memory_search` 从 **约 28 分钟** 降到 **约 2.2 秒**，dsh 里的 `mcp__xilian__*` 工具全部可用。

---

## 1. 问题现象

dsh 侧挂载了昔涟 MCP 后，`memory_stats` / `audit_recent` 秒回，但两个检索工具实际不可用：

- 直接调用 `retrieve()`：命令行 120s 超时仍未返回
- 走 MCP `memory_search`：会顶穿 harness 的工具超时（`cordis.patch.yml` 里配的 `toolCallTimeoutMs: 120000`）

## 2. 根因（全部为实测数据）

| 环节 | 实测 |
|---|---|
| 单条文本嵌入 `/api/embeddings` | **2.17 s / 条** |
| 全库 771 条顺序执行 | **≈ 1676 s（约 28 分钟）** |
| Ollama 原生批量 `/api/embed`（64 条/次） | 2.8 s → **0.044 s / 条** |
| 8 线程并发单条请求 | 0.28 s / 条 |

直接原因在 `retrieval.py`：

```python
# 修复前
def _embed_candidates(candidates):
    for r in candidates:                      # ← 771 次串行 HTTP
        _candidate_vecs[mid] = _embed_text(text)
```

`retrieve()` 每次检索都会对 **Phase1 全量候选**（默认上限 1000，本库 771 条）逐条重新生成向量，既没有批量，也没有任何持久化，所以每次检索都在从零重算 28 分钟的活。

排查中还挖出两个隐藏问题：

1. **维度不一致会静默丢结果**：`_fallback_embed()` 是 384 维 hash，而 bge-m3 query 是 1024 维。
   一旦 Ollama 失败，`_cosine_sim` 维度不匹配 → `sim = 0.0` → 被 `_MIN_SIM_THRESHOLD = 0.15` 全量过滤。
   表现是「检索没有任何结果」，而不是报错，极难排查。
2. **单条脏文本会毒掉整批**：`memory_id = b8b248bd79f9` 这条记忆嵌入时，Ollama 返回
   `HTTP 500 {"error":"failed to encode response: json: unsupported value: NaN"}`。
   批量请求里只要有一条触发 NaN，**整批 64 条一起失败**（首轮预热实测 707 成功 / 64 兜底）。

## 3. 做了什么改动

| 文件 | 改动 |
|---|---|
| `services/B4_dual_gate_retrieval/embed_cache.py` | **新增**：SQLite 向量落盘缓存 |
| `services/B4_dual_gate_retrieval/retrieval.py` | 改造：批量嵌入 + 缓存 + 二分重试 + 维度一致性修复 + 余弦加速 |
| `services/B4_dual_gate_retrieval/build_cache.py` | **新增**：缓存维护 CLI（预热 / 查看 / 清空 / 试检索） |
| `services/B4_dual_gate_retrieval/__init__.py` | 导出 `warm_embed_cache`、`embed_cache`、`candidate_text` |
| `services/C2_mcp_server/mcp_server.py` | `memory_stats` 增加 `embed_cache` 覆盖情况 |
| `config.yaml` | 新增 `retrieval:` 段（三个开关） |
| `~/.dsh/profiles/web/cordis.patch.yml` | `failOnStartupError: false → true`（**项目外**，见 §6.6） |

### 3.1 向量落盘缓存 `embed_cache.py`

- 存储：`data/index/embed_cache.db`（与 `header.db` 并列的 sidecar，**不改动既有 schema**，可随时删除重建）
- 键：`sha256(模型名 + "\x00" + 文本)` → 文本或模型任一变自动失效，不会读到脏向量
- 序列化：`array('f')` 二进制 blob。**注意**：这里刻意不转成 `list`，771×1024 转 list 要 2.3s，保持 C 缓冲只要 **9ms**
- 附带 `stats()` / `coverage(texts)` / `clear()` / `prune()` / `enabled()`

### 3.2 `retrieval.py` 改造

1. **三级取向量**：进程内 `_candidate_vecs` → 落盘缓存 → Ollama 批量接口 → hash 兜底
2. **新增 `_ollama_embed_batch()`**：走 Ollama 原生 `/api/embed`，一次请求多段文本
3. **新增 `_embed_batch_with_retry()`**：整批失败时**二分重试**，把 NaN 毒文本隔离到单条，不再连坐 63 条
4. **维度一致性修复**：维度不匹配时用同一套 hash 编码重算 query 再比，并把该条标 `_degraded=True`；不再静默判 0 分
5. **余弦加速**：候选模长缓存（`_VEC_NORMS`）+ `sum(map(mul, a, b))` 点积，替代每次重算 `sqrt` 的生成器循环
6. `retrieve()` 返回值新增 `embed_stats` / `rank_stats`，便于自查

### 3.3 配置开关（`config.yaml`）

```yaml
retrieval:
  embed_cache: true    # 候选向量落盘缓存（data/index/embed_cache.db）
  embed_batch: 64      # 单次 /api/embed 送多少条文本
  embed_workers: 4     # 并行批次上限
```

## 5. 怎么用

在 `v2` 目录下执行：

```bash
# 预热全库向量（批量导入旧记忆后跑一次，约 10~30s）
python -m services.B4_dual_gate_retrieval.build_cache --warm

# 查看缓存概况
python -m services.B4_dual_gate_retrieval.build_cache --stats

# 试一次检索并看耗时明细
python -m services.B4_dual_gate_retrieval.build_cache --search "书房 记忆 架构"

# 清空缓存（换嵌入模型后必须执行）
python -m services.B4_dual_gate_retrieval.build_cache --clear
```

不预热也能正常工作：检索时会自动按需补算并写回缓存，只是第一次调用多花约 10~30s。

MCP 侧同样可自查：

```
mcp__xilian__memory_stats  → embed_cache: {cached: 770, missing: 1, coverage: 0.9987, size_mb: 3.36}
```

**改了 B4 代码后必须重启 MCP 子进程才会生效**（Python 进程不会热加载）：

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like '*C2_mcp_server*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

dsh 侧 `reconnect.enabled: true` 会在约 1 秒后自动重启它（本次排查中验证过多次）。

## 6. 已知限制与遗留问题

### 6.1 有 1 条记忆无法生成向量

`memory_id = b8b248bd79f9`，文本「用户要求完全重做记忆系统的识别流程…」。
Ollama bge-m3 对这条输入返回 NaN（HTTP 500），单条重试同样失败，属于 Ollama/模型侧问题。
现状：该条走 384 维 hash 兜底，不影响其它 770 条的检索质量。
每个 Python 进程首次检索会为它多花约 2.2s 的失败重试，之后进入进程内缓存不再重试。

### 6.2 query 嵌入的 2.2s 是当前下限

模型已常驻 GPU（`ollama ps` 显示 100% GPU / 1.3GB），加 `keep_alive: 1h` 实测无改善，
单次请求固定开销就是约 2.1~2.3s。这是每次检索的固定成本，暂无解。

### 6.3 `config.yaml` 的 LLM Key 仍是占位符

第 21 行仍是 `<your-api-key>`，走 LLM 的链路（`mcp_tools/chat`、温提炼）会失败。
**需要到 DeepSeek 控制台轮换新 Key 后填入**（原 Key 已泄露在对话里）。

### 6.4 `loader._resolve_paths` 会忽略 `config.yaml` 里的 `paths`

`services/shared/config/loader.py:103` 取的是 `_DEFAULT_CONFIG` 的默认值，而不是用户配置：

```python
defaults = _DEFAULT_CONFIG.get("paths", {})
p = defaults.get(key, "./data")     # ← 不读 config["paths"][key]
```

当前 `config.yaml` 的取值与默认值恰好一致所以没暴露。若以后要改数据目录，这里会是个坑，建议单独修。

### 6.5 记忆分层尚未产生

`get_layer_distribution()` 返回 `{"hot": 771}` —— 全部为 hot，L1/L2/L3 分层逻辑还没跑出结果。
`memory_search(depth="L2"/"L3")` 的深挖依赖每条记录的 `content_path` 是否已写入。

### 6.6 `failOnStartupError: true` 的取舍

`~/.dsh/profiles/web/cordis.patch.yml` 里已把 MCP 条目的 `failOnStartupError` 改为 `true`。
好处：MCP 挂载失败会让 dsh 启动直接报错，不再像这次一样「工具静默消失」。
代价：Python 环境坏掉时整个 Web GUI 起不来。

改回原值只需把那一行改成 `failOnStartupError: false`。

### 6.7 与 B3 README 的关系

B3 README 里「FAISS 向量索引」仍标注为待实现。本次没有引入 FAISS，
而是用 SQLite sidecar 缓存向量 + 纯 Python 余弦（本机未安装 numpy）。
771 条规模下这已经足够（精排阶段实测 < 50ms）；若记忆量级涨到十万条，再考虑 FAISS/ANN。

### 6.8 【本次新发现】`memory_drilldown` 读不了 L2/L3（未修，需先定方案）

实测调用 `memory_drilldown(memory_id="3ed603eecc44", depth="L2")` 返回：

```
"error": "无法读取 content_path: Extra data: line 2 column 1 (char 277)"
```

原因有两层：

1. `mcp_server.py` 里对 `content_path` 用的是 `json.load(f)`，但 V1 冷库文件是 **JSONL**
   （每行一个 JSON 对象）：
   ```
   {"id": "202605100001", "time": "...", "user": "...", "assistant": "..."}
   {"id": "202605100002", ...}
   ```
2. `content_path` 存的是**整天的会话文件**（`...\shufang-os\backend\data\cold_vault\2026-05-10.jsonl`，
   V1 的另一个项目目录），而不是这一条记忆对应的片段。SQLite 表头里没有记录
   `memory_id → JSONL 行号 / 对话 id` 的映射，所以即使改成逐行读，也不知道该取哪一行。

所以这不是一个纯 bug，而是「L2/L3 的物理存放约定」还没落地。可选方案：

- **方案 A**：迁移时把每条记忆的原始片段单独落一份到 `data/cold_vault/<memory_id>.json`，
  表头 `content_path` 直接指向它（改动最小，drilldown 立刻可用）
- **方案 B**：表头增加 `source_ref` 字段（JSONL 路径 + 行号），drilldown 按行号取
- **方案 C**：drilldown 退化为「按 summary 反查同 session/同时间桶的周围若干行」返回上下文

建议先做 A。当前 `depth="L1"` 是正常的（只读表头），只有 L2/L3 受影响。
