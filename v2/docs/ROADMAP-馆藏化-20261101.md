## 2. 判定依据：为什么现在是 RAG

### 2.1 对照书里的「组织整理四法」（《图书馆学导论》p.32）

| 方法 | 书上的定义 | 现状 | 结论 |
|---|---|---|---|
| 分类法 | 对知识体系作系统划分 | P5 十类 + 主副类 | **达标** |
| 描述法 | 描述**内容特征 + 文献实体特征** | 45 字摘要（内容特征的极简版），实体特征近零 | **半** |
| 编码法 | 译成机器可辨认的代码 | 有向量/FTS/id，无可交换的著录格式 | **半** |
| 引文法 | 按引用关系揭示作品间关系 | 无 | **缺** |

### 2.2 对照书里的「图书馆目录五功能」（p.46，卡特三分 + IFLA + Svenonius）

| 功能 | 现状 | 结论 |
|---|---|---|
| 确认（找到） | 四路召回 + 重排 | **强** |
| 聚合（同主题全给） | facets 只计数，给不出全集清单 | **缺** |
| 选择（按版本/特征挑） | 只有相关性排序 | **半** |
| 获取（取全文） | `has_l3=100%`，7 ms 取回原文 | **强，超过一般 RAG** |
| 导航（等同/相关/等级） | `relations` 有数据但没接线 | **缺** |

### 2.3 一句话结论

> 它的唯一入口是「这句话和哪条最像」——那只实现了目录五功能里的**「确认」**，而「确认」恰好就是 RAG 的全部。
> 补上 **聚合** 就变成目录；补上 **引文** 就变成引文索引（加菲尔德 SCI 的位置）。

## 3. 路线图：L1 → L6（由简到繁）

> 排序原则：**先做「不需要新模型、不推翻检索、今天就能验收」的**；把会动语义的排到最后。

### 3.0 三条线怎么咬合（**别让它们变成三个平行的抽屉**）

2026-11-01 定的合成关系：

```
        L2 collocate ──────> 「这个主题里有哪些条目」      （集合）
              │
              ├── L1 citations ──> 「这些条目内部谁接着谁」 （结构）
              │
              └──────────────┐
                             ↓
                   L3 catalog_export ──> 带谱系的著录清单 （成品）
```

三条硬规则，写代码时按这个来：

1. **L3 必须调用 L2，不许自己再写一遍查询。**
   否则「导出 41 条、聚合说 40 条」这种打架迟早发生。`catalog.py` 里是
   `res = collocate(target, kind=kind, ...)` —— **单一真源**。
2. **L3 的 `relation` 必须来自 L1，不是 `memories.relations` 那个自由文本字段。**
   那个字段 56% 有值但**检索零引用**、也没人维护；L1 的边是抽取出来、带置信度的。
3. **断言 `L3.total == L2.total`**，不一致就是 bug，不是「数据有点旧」。
   `scratch/test_l123_integration.py` 里就是这么卡的。

### 3.1 接线：让 `libmem_search` 自己带上 L1/L2（2026-11-01 已做）

建了三个工具不等于它们会被用上 —— **模型不会记得调它们**。所以接线分三层，
按"风险从低到高"排，**只做了前两层**：

| 层 | 做法 | 风险 | 状态 |
|---|---|---|---|
| ① **结果增强** | `memory_search` 返回里附 `enrichment.citations`（每条结果的引文邻居 id） | 零（只加字段） | ✅ 已做 |
| ② **覆盖面自检** | 同上，附 `enrichment.topic`：「这个主题共 42 条，只给了你 8 条」 | 零（只提示，不改结果） | ✅ 已做 |
| ③ **意图分流** | 识别「一共/全部/都有哪些」→ 直接走 `collocate`；「从哪来」→ 直接走 `citations` | **高**（判错就答错） | ❌ 暂不做 |

**为什么先不做 ③**：静默换管道最危险 —— 用户问「书房OS 最近怎么样」，被误判成枚举题
直接甩 42 条，比只给 8 条差得多。而 ② 已经能覆盖 ③ 的大部分价值：**不改变你问什么，
只告诉你少了什么**，由调用方自己决定要不要展开。

**为什么接在工具层而不是 `retrieve()`**：`retrieve()` 是所有调用方（MCP/MAP/FastAPI/CLI）
的汇合点，动它等于同时改所有契约；`memory_search` 只是**追加字段**，老调用方忽略即可。
配置开关：`retrieval.enrich: false` 可整体关掉。

**实测成本（这是关键）**：

| 场景 | 开销 |
|---|---|
| `_enrich_search` 自身 | **1.1 ms** |
| 端到端（开 vs 关） | 176.6 vs 178.6 ms —— **在噪声内** |
| 冷启动首次（建实体索引） | 59 ms，每个进程一次 |

**两个缓存坑（第二次同款的坑，值得单独记）**：

1. **缓存不能用 `write_epoch` 做失效键。**
   检索会**升温写库**（heat+1），纪元每次都变 → 缓存永远不命中 → 每次 search
   都重建 906 行实体索引，实测给检索加了 **~70 ms**（188 → 258）。
   改成 **TTL(120s) + 写入侧显式 `invalidate_entity_index()`**（接在 `warm_indexer` 里）。
   > 这跟 L1 那个「时间基线不能用 created_at」是同一类错误：**把"经常变的东西"
   > 当成了"该触发重算的东西"**。
2. **`_TOPIC_CACHE` 同理**，改用 TTL(60s)。

**验收**：`scratch/test_enrich.py`、`scratch/bench_enrich_cost.py`。

### L1 · 引文边（最小、最不像 RAG）

> **状态：已完成（2026-11-01）** —— 见文末「完成记录 · L1」。

**依据**：书 p.32「引文法」；p.44「引文与被引文献之间存在主题关联性，正是这种关联性，使引文成为一种有效的检索入口」；p.45 加菲尔德做 SCI。

**做什么**：给记忆之间建「谁引用了谁」的边。**不接检索，纯建数据 + 一个读工具。**

```sql
CREATE TABLE IF NOT EXISTS citations (
  from_id    TEXT NOT NULL,          -- 引用方（较新）
  to_id      TEXT NOT NULL,          -- 被引用方（较早）
  kind       TEXT NOT NULL,          -- explicit | successor | same_thread
  confidence REAL DEFAULT 0.5,
  evidence   TEXT,                   -- 抽取依据（原文片段 / 共现实体）
  created_at TEXT,
  PRIMARY KEY (from_id, to_id, kind)
);
CREATE INDEX IF NOT EXISTS idx_cit_from ON citations(from_id);
CREATE INDEX IF NOT EXISTS idx_cit_to   ON citations(to_id);
```

**抽取规则（三档，置信度递减）**：

| kind | 规则 | 置信度 |
|---|---|---|
| `successor` | 同 session 相邻两条，后者更晚且 `core_entities` 交集 ≥ 1 | 0.6 |
| `explicit` | 后条原文含指代词（上次/刚才/之前那个）+ 前条实体 | 0.9 |
| `same_thread` | 同 task_type + 同月 + 实体交集 ≥ 2 | 0.2 |

**落点**：B2 提炼完成后钩一次（`services/B2_warm_extract/`），失败不得影响写入。
**新增工具**：`libmem_citations(memory_id)` → 上游/下游各若干条（工具注册在 `services/C2_mcp_server/libmem_tools.py` 的 `TOOLS`）。

**验收（三条，全过才算完成）**：
1. `citations` 行数 > 0，且所有 `to_id` 的 `source_date` ≤ `from_id` 的 `source_date`（时间不能倒流）；
2. 人工抽查 10 条，每条都能说清「为什么连这道边」；
3. **检索完全不受影响**：同一批 10 条查询，top-8 与做之前逐条相同。

**回滚**：`DROP TABLE citations;` + 撤掉 B2 里的钩子（一行）。
**预计**：半天。

### L2 · 聚合清单（把「计数」变成「全集」）

> **状态：已完成（2026-11-01）** —— 见文末「完成记录 · L2」。

**依据**：书 p.46 卡特的**聚合功能** ——「揭示图书馆对于某一特定作者、某一特定主题或某一类型的文献拥有哪些馆藏」。

**做什么**：新增 `libmem_collocate(target, kind, limit=None)`，**返回全集而不是 top-k**，按时间倒序，带分页游标。
数据源优先 `terms/mem_terms`（精确），退化到 `memories.core_entities`（模糊）。

**关键**：这是**唯一一个「越多越对」的入口**。现在的所有工具都在做「选最好的 8 条」，而聚合要的是「一条都不许少」。

**验收**：
1. `collocate("书房OS")` 返回条数 = 独立 SQL 核对的条数（注意：`书房OS` 与 `书房 OS` 两种写法要能合并，见 L5）；
2. 分页翻到底，无重复、无遗漏（用 `COUNT(DISTINCT)` 交叉验算）；
3. 输出里带 `class` 和 `source_date`，可以当清单直接读。

**回滚**：只删工具注册，数据零改动。
**预计**：半天。

### L3 · 著录导出（把「一条记忆」变成「一条著录」）

> **状态：已完成（2026-11-01）** —— 见文末「完成记录 · L3」。

**依据**：书 p.42 图 2.4（MARC 编码）、p.43（联机公共目录的显示格式）、p.32 描述法。

**做什么**：新增 `libmem_catalog_export(target, format="md"|"json")`，把一个主题/类目的全部条目导出成一份**著录清单**（极简 Dublin Core）。

| DC 元素 | 取哪个字段 |
|---|---|
| `identifier` | `memory_id` |
| `title` | `summary` |
| `subject` | `descriptions.terms` / `class` |
| `date` | `source_date` |
| `relation` | `memories.relations` |
| `source` | `session_id` |
| `description` | 冷库原段落（`has_l3` 保证可取） |

**验收**：
1. 导出 20 条以上，字段缺失率 < 20%；
2. 导出的文件能被一个**没读过代码的人**看懂「这是什么、什么时候、从哪来」；
3. `json` 格式可被 `json.load` 无警告解析。

**回滚**：删工具。
**预计**：1 天。

### L4 · 参见边（把「导航」接上）

**依据**：书 p.46 Svenonius 的**导航功能** ——「通过书目数据间的**等同、相关、等级**关系，从已知作品导向其他作品」。

**做什么**：在 `terms` 之间建边（同义词已有 = 等同边；共现 PMI 自动生成 = 相关边；分类层级 = 等级边）。查询 A 时，输出里带「参见：B, C」。

**注意**：等同边（别名）已经有了（`terms.aliases_json`），**不要重建**；这里补的是**相关边和等级边**。

**验收**：
1. 随机抽 10 个词，每个都能给出 3 个参见；
2. 参见里**不能全是同义词**（否则等于没做导航）——抽检至少 5 个是「真不同但相关」；
3. 输出带边类型，让用户能分辨「这是同义」还是「这是相关」。

**回滚**：删边表 + 删工具。
**预计**：1~2 天。

### L5 · 规范控制闭环（查询改写）

**依据**：书 p.39 图 2.3「受控词表示例」；p.32 编码法。

**做什么**：现在 `B8.catalog_search` 是**第 5 路候选**，而且 `catalog_bonus = 0`（实测无收益，注释在 `config.yaml`）。改成**查询改写**：进检索前把 query 里的实体先过一遍别名表，映射到 canonical 再检索。

这是**改写查询**，不是**增加召回路**——两者差别很大，前者不改变排序结构。

#### ★ 定位：款目表是**每个用户私有的、AI 自建的**底层产物（2026-11-01 定）

这一条改变了 L5 的性质，动手前必须先读懂：

1. **它不是插件自带的数据，是每个用户的那一份。**
   插件分发的是**机制**（何时建、怎么合并、怎么审、怎么回滚），**不是款目表本身**。
   张三的「款目」里有他的项目名，李四的有他的。把它做成固定词表发出去，等于把 A 的私人世界塞进 B 的目录 —— 那是错的。

2. **它由 AI 从这个用户的记忆里自行建构**，不是人工填表。
   人要做的是**点头/驳回**，不是逐条录入。

3. **绝不能后台静默跑。**
   建构款目要读全库、要判断「这两个名字是不是同一个东西」，那是**烧 token 的活**。
   静默跑 = 用户在不知情的情况下被扣费，而且做出来的东西他也没看过、不会认。
   所以必须是：**定期提醒 → 用户同意 → 只做增量的一小批 → 给出待确认清单**。
   提醒的触发条件（三选一，可配）：
   - 新增记忆累计 ≥ N 条（默认 100）；
   - 新出现的别名冲突 ≥ M 组（默认 10）；
   - 距上次建构 ≥ 30 天。
   **提醒本身不消耗算力**（只是数数），同意之后才排队。

4. **增量，不全量。**
   每次只处理「新出现的写法」和「上次没通过的候选」，已有款目直接复用。
   全量重算既贵又会让已确认的结果漂移。

5. 一句话：**款目表是这个软件的底层设施，不是某个人为此专门做的一份表。**

#### 验收（A/B 对照）

1. 「书房OS」「书房 OS」「libmem」「Libmem」两组写法，改后返回**同一批** top-8；
2. 召回率不降（用现有 10 条基准查询对比 top-8 重合度 ≥ 90%）；
3. 耗时增加 < 5 ms；
4. **提醒可关闭**：配置 `retrieval.authority_suggest: false` 后，插件不再提这件事，且不影响任何既有功能。

#### 风险

- 别名表若乱合并（把「版本号 V1.2」并进「V1.3」），会引入错误召回。所以必须**先建待确认队列**，自动归并只处理高置信（大小写/空格/连字符级）的，其余一律进队列等人点头。
- **别把它做成"后台常驻任务"**：一旦进了定时任务，就等于默认为所有用户持续烧钱。只做「提醒」，不做「自动执行」。

**回滚**：配置开关 `retrieval.authority_rewrite: false`（同时关掉提醒）。
**预计**：1~2 天 + 一次 A/B。

### L6 · 排架（主题排架，最后做，也最危险）

**依据**：书 p.45 ——「由于在空间上实现了相同或相关作品的聚合，按分类排列的文献集合可以帮助用户**在浏览中发现相关文献**」。

**问题**：现在 `layer = cold/warm/hot` 是**按热度**排的。浏览时挨在一起的是「最近都被翻过」的东西，不是同主题的东西——**等于没有浏览功能**。

**做什么（收紧版）**：**只改浏览排序，不改 `layer` 语义**。
- `library browse` 增加 `order_by="class"`，同 `class` 内按 `source_date` 排；
- `layer` 保留为「热度维度」，供剔旧/迁移使用，**一个字节都不动**。

⚠️ 不要试图把 `layer` 改成主题分层：`decay_memory.py`、`migrate_layers()`、`verify-heat-ranking` 全都依赖它现在的语义，改一处崩三处。

**验收**：同一类目下浏览 20 条，肉眼可见「它们讲的是同一件事」。
**预计**：半天（如果只做排序）。

## 4. 红线（每一条都是踩过的坑）

1. **不许破坏 B7 审计链**：`search` 与 `write(heat)` 必须同 `trace_id` 落盘，`integrity_hash` 必须非空。这是「重试不重复升温」的唯一证据。
2. **不许破坏 `has_l3` 追溯**：任何新入口都要能回到冷库原文。
3. **不引新依赖**。numpy 之类实测无收益（瓶颈是重复劳动不是数学），而且这个解释器里根本没装。

5. **任何写库改动先在副本上跑**：

   import sqlite3
   src = sqlite3.connect(REAL); dst = sqlite3.connect(TMP)
   with dst: src.backup(dst)

6. **性能不得回退超过 10%**：改完必须跑 `scratch/profile_search.py` 对比 §1.4 的基线。
7. **不要信摘要**。摘要中位 45 字，是「提示」不是「内容」；判断事实要 `libmem_drilldown(depth="L3")`。

**三条踩到的坑（下次别重复）**：

1. **`session_id` 全库为空（906/906）。**
   原设计「同 session 相邻两条」一条边都打不出来。冷库是**按天**一个 `.jsonl`，
   所以退而用 `content_path` 当会话键（54 个文件 = 54 段会话流）。
   **这个替代必须写进注释**，否则下一个人会以为边是按真实会话分的。
   → 要修的真问题是**写入侧没带 session_id**（B1 落盘时丢了），那是另一件事。

2. **时间基线要用 `source_date`，不能先比 `created_at`。**
   `created_at` 是**提炼时间**，`source_date` 是**事情发生的时间**。补灌历史时
   两者顺序会打架 —— 第一版用 created_at 排，立即造出 1 条「后发生的引用了先发生的」
   （违反红线 1）。顺序必须是 `source_date → created_at → memory_id`。

3. **「同会话所有前驱都连」会把谱系变成网。**
   第一版 906 条记忆长出 840 条 successor 边，等于把一天之内所有条目两两相连 ——
   那不是引文，是噪音。改成：`successor` **只连最近的那一条**（谱系要链不要网），
   `explicit` 最多 2 条，`same_thread` 最多 2 条。

**已知未做**：

- `explicit` 边现在是 **0 条**：把「继续/再说」从指代词表里去掉后，没有一条同时命中
  「同会话 + 明确指代 + 共享实体」。要么放宽（会混进假阳），要么等 `session_id` 修好再看。
- 边是**单向**（from → to），没有反向索引的查询优化；库到万级要给 `to_id` 加覆盖索引。

## 完成记录 · 款目表与排架：公版 + 私版（2026-11-01）

用户定的定位：**「一个通用表走天下」不成立**，因为每个人的记忆不同；
但**公版仍然必须有**，否则新用户一装上就是空白。所以要两层。

### 新增的文件与数据

| 层 | 文件 | 内容 | 谁生成 |
|---|---|---|---|
| 公版款目 | `data/authority/general.yaml` | **36 条**：只收跨用户成立的写法差异（`github/gh`、`rag/检索增强生成`） | 随插件分发 |
| **私版款目** | `data/authority/private.yaml` | **241 条**：这个用户的项目名/自造词（`书房 OS`、`记忆系统`） | **AI 从记忆里建** |
| 公版排架 | `data/shelf/general.yaml` | 8 个类目的**排架次序 + 一句话说明** | 随插件分发 |
| 私版排架 | （派生） | 二级类目由 `B8.build_subclasses` 从**用户数据**长出来 | AI |

**纪律（写在 general.yaml 表头）**：公版**只收**「跨用户成立的工具名/格式名/通用概念 + 写法差异」，
**绝不收**任何人的项目名、人名、自造词 —— 那些是私版的。

### 实测

```
公版 36 条；私版 241 条（从 911 条记忆里扫出 2582 个实体组）
resolve('书房OS') → canonical='书房 OS', aliases=['书房OS'], scope=private
resolve('GitHub') → canonical='github',  aliases=['GitHub','gh'], scope=general
```

### 「成长」是怎么发生的（不烧钱的闭环）

1. `authority_status` → `suggest()` **只数数**（不调模型、不花 token）：
   - 新出现 ≥10 组写法分裂 / 距上次 ≥30 天 / 从没建过 → `should_prompt=true`
2. 把 `reasons` 说给用户听（"新出现 44 组写法分裂，要建一次款目表吗？"）
3. 用户点头 → `authority_build` 才真正跑（**增量**，只处理没进表的）
4. 写 `private.yaml` + 落 `authority` 表，下次 `suggest` 自动安静

**建完之后实测 `suggest.reasons == []`** —— 提醒会自己消失，不会天天骚扰。

### L6 排架接在哪

`_library_browse(order_by="class")` 不再按类名字母序，而是按 `shelf.rank()` 的**公版次序**，
同类内仍按创建时间倒序。开关 `features.subject_shelf` 默认 **false** ——
关着时强制回时间序，**默认行为一个字节没变**。

### 一句话总结这个设计

> **公版是机制（写法怎么归一、类目怎么排），私版是资产（这个人的世界长什么样）。**
> 插件发的是机制；AI 装上去之后，用这个人的记忆把资产一点点长出来。
