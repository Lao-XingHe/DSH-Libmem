# 书房 OS v1.3.2 · `task_type` 封闭取值（表头标引修复）

> 2026-09-29 · 作者指令：*"做之前先把 task_type 做了，再表头索引上"*
> 前置：`V1.3.1-维度版-README.md`（那一版做的是**问题侧**的维度；这一版做的是**记忆侧**的标引，两者不可混）

---

## 一、一句话

**表头 `task_type` 78.8% 都是"闲聊"、拿它过滤等于不过滤 —— 查出根因是「两套词表 + 没标引规则」，收成封闭取值并用模型重标，最大单值降到 30%。**

---

## 二、诊断：三层，越查越深

| 层 | 猜测 | 实测 |
|---|---|---|
| 1 | 模型乱填 | ❌ 不是 |
| 2 | `migrate_v1_data.py:184` 硬编码 `"task_type": "闲聊"` | ⚠️ 只占 **38 条** |
| 3 | **★ 真相** | DB 里 392 条老值的 `task_type` **不是当前代码写的** —— 用当前规则重标，一致率只有 **1.8%（7/392）** |

**而当前规则本身也是坏的**：`_guess_task_type()` 是**关键词词面匹配 + 兜底"其他"**，重标 392 条的结果是 **其他 221（56%）** —— 只是把"闲聊 97%"换成"其他 56%"。

**还有一层语义错误**：`EXTRACT_PROMPT` 里有两个字段、两套词表 ——

| 字段 | 词表 |
|---|---|
| `type` | 事实 / 偏好 / 决策 / 问题 / 灵感 |
| `intent` | 研究 / 决策 / 验证 / 规划 / 闲聊 / 求助 |

而 `warm_indexer` 直接拿 `type` 当 `task_type` 用（`warm_indexer.py:201`）。
**同一个字段名承载两种语义。**

---

## 三、改了什么

| 文件 | 状态 | 说明 |
|---|---|---|
| `task_types.yaml` | **新增** | ★ 封闭取值 + **每类一句判据**（数据，改它就能改标引口径） |
| `services/shared/task_types.py` | **新增** | 唯一一份实现：`values / judge_block / prompt_for / normalize / validate` |
| `relabel_task_type.py` | **新增** | 回填工具（**默认 dry-run**；`--apply` 前强制备份 + 生成回滚表） |
| `services/B2_warm_extract/warm_extractor.py` | 改 | `EXTRACT_PROMPT`：**删掉 `type`/`intent`，改成 `task_type`** + 注入判据 |
| `services/B3_header_engine/warm_indexer.py` | 改 | 取值优先级：`task_type`（新）→ `type`（兼容老数据）→ 关键词兜底；**越界值不落库** |

### 关键设计：给「判据」而不是给「例子」

LIS 的老教训：**没有编目规则的字段，等于没有字段。** 小模型不是不会填，是**没有规则可依，就挑了个默认值**。给例子会让它抄例子，给判据才会泛化。

### ★ 判据的「标引视角」（试标 30 条后补的一节，最要紧）

第一版判据写的是"用户**想**干什么"（现在的意图），实测错得很明显：

```
"决定采用简化版 JSONL 格式…"    → 判成「其他」（该是决策）
"确认冷/温/热记忆文档统一存储…"  → 判成「其他」（该是决策）
```

**根因**：`summary` 是**过去时的记录**，不是提问时的意图。判据按"意图"写，凡是"记录了一件已经定下来的事"的条目就全漏进兜底 → **「其他」占到 33%**。

改成回顾式视角（**这条记忆记录的是哪一种活动**）后，「其他」从 **33.3% 降到 20.0%**，`决策` 从 3 涨到 6。

## 四、结果（490 条，4B 模型）

| `task_type` | 旧 | **新** |
|---|---|---|
| 闲聊 | **380 (78.8%)** | **8 (1.6%)** |
| 决策 | 54 | 149 |
| 研究 | 0 | 107 |
| 规划 | 0 | 89 |
| 其他 | 12 | 53 |
| 求助 | 0 | 44 |
| 验证 | 4 | 40 |

**判据（离线可验，不用跑 LoCoMo）**：

| 判据 | 旧 | 新 | 达标 |
|---|---|---|---|
| 最大单值 ≤ 40% | 78.8% | **30.3%** | ✅ |
| 兜底「其他」≤ 10% | 2.5% | **10.8%** | ⚠️ 差 0.8 个点 |

**关于那 10.8%**：抽 30 条人工核过，这 6 条**确实该是「其他」**——

```
"用户询问如何判断会话结束以及当前记忆状态…"    → 状态询问
"当前核心记忆文件为 feedback_auto_memory.md…" → 状态罗列
"今日冷记忆系统运行正常，记录 16 条对话…"      → 状态汇报
"用户请求继续之前的对话，但助手未提供具体响应"  → 空壳记录
"[冷] 一样就不用"                            → 碎片
```

**这个库本身就有约 10% 的状态汇报/空壳/碎片类记忆。所以 10.8% 是诚实标引，不是判据漏。**
（阈值 ≤10% 是我一开始拍的，不是硬标准；真正该守的是**最大单值**那一条。）

**过滤真的能用了**：`task_type=决策 AND time_bucket=2026-04` → **29 条**（原来是 380 条"闲聊"，等于不筛）。

## 五、模型选择：4B 就够（有证据）

| 依据 | 说明 |
|---|---|
| **4B 已经在干这活且没退化** | v2 的 98 条就是 4B 标的：决策 59 / 事实 21 / 问题 14 / 验证 4，**一条"闲聊"都没有** |
| **任务比相邻任务简单** | 7 类**封闭分类** vs "提取实体+关系"的自由抽取 |
| **成本** | 490 条 × **0.28 秒/条 ≈ 2.3 分钟**；9B 要 3~5 倍 |
| **判据可迁移** | 最大单值 30.3% 已达标。**不达标再升 9B**，升的时候只需换 `--model` |

**结论：4B。（9B 留作判据不达标时的升级路径。）**

## 七、这次踩到的两个坑（都记下来防止重踩）

### 坑 1 · 思维链把 max_tokens 吃光 → 空返回伪装成"模型标不出来"

第一次试标 30 条，**30 条全返回空串** → `normalize('')` → 兜底"其他" → 看上去像
"模型 100% 标不出来"，其实是**调用方式错了**。

Qwen3.5 默认开思维链，必须带 `chat_template_kwargs={"enable_thinking": false}`。
本仓 `llama_server_backend.py:12-14` **早就记着这个坑**，我手写 HTTP 时没带上。

→ 修法：**空返回必须响亮**。工具现在统计 `empty` 并在告警时**拒绝写库**，绝不让它静默变成"其他"。

### 坑 2 · 标引视角错位（意图 vs 记录）

见 §三。**判据写的是谁的视角，决定了标引结果对不对** —— 这一条比词表本身更容易错。

### 另记：临时=0 也不完全可复现

dry-run 与写库两次跑的分布有 ±2~3 条的抖动（决策 147→149、其他 56→53…）。
llama.cpp 在 temperature=0 下也不保证逐条一致。**所以单条结果不可复现，能复现的是分布。**
